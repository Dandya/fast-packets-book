## Классический BPF

### Устройство технологии

Технология классического BPF (cBPF) была описана в 1992 году в статье «The BSD Packet Filter: A New Architecture for User-Level Packet Capture». В основе технологии лежит построение дерева высказываний о пакете (см. рисунок [1]). Дерево строиться по логическим высказываниям в фильтре пользователя и преобразуется в набор инструкций, которые после выполняются виртуальной машиной при анализе сетевого пакета [1].

![Пример дерева высказываний для фильтра «host foo» [1].](images/cBPF_tree_example.jpg)

Каждая инструкция состоит из восьми байт:

1. код операции (16 бит);
2. положительный сдвиг от текущей инструкции в случае истинного исхода (8 бит);
3. положительный сдвиг от текущей инструкции в случае неистинного исхода (8 бит);
4. параметр (32 бит).

На основе поля с кодом операции виртуальная машина выполняет одно из действий (см. рисунок [2]):

1. загрузка значения в регистр;
2. сохранение и загрузка значения в память;
3. математическое вычисление;
4. переход к следующей инструкции;
5. запись значения одного регистра в другой;
6. выполнение возврата.

![Структура операций с их аргументами [1].](images/cBPF_operations.png)

Виртуальная машина имеет два регистра с длинами по 4 байта и памятью с длиной 64 байта и выполняет все инструкции последовательно. Из-за устройства инструкции виртуальная машина не может оказаться в состоянии цикла, что позволяет использовать эту технологию в ядре операционной системе, ожидая, что виртуальная машина выполнит все свои действия за детерминированное время. Кроме того, виртуальная машина спроектирована таким образом, чтобы обеспечивать легкое добавление правил фильтрации новых протоколов, иметь реализацию через цикл `for` и операцию `switch` в языке «C» и использовать регистры процессора в процессе работы виртуальной машины.

В настоящее время в ядре «Linux» фильтры, основанные на технологии cBPF, имеют называние «socket-filters» [2].

### Создание фильтра

Фильтр cBPF задается массивом инструкций. При этом длина этого массива в ядре «Linux» ограничена и имеет максимальное значение в 65535 элементов.

Но основным способом создания фильтров данного типа является преобразование строки с логическими выражениями о заголовках пакета в массив инструкций. Такое преобразование реализовано в библиотеке «Libpcap» (см. `contrib/libpcap/gencode.c`) с помощью функции `pcap_compile`.

При применении каждой из рассмотренных систем захвата сетевого трафика необходимо использовать библиотеку «Libpcap», чтобы преобразовать строку с фильтром в массив инструкций [3].

### Фильтрация в пространстве ядра

В пространство ядра массив инструкций фильтра cBPF попадает при использовании системного вызова `setsockopt` с параметром `SO_ATTACH_FILTER`. При возврате фильтром нуля пакет будет отброшен, а при возвращении числа, отличного от нуля, пакет либо будет усечен, если число меньше длины пакета, либо поступит в сокет полностью. Из-за связи с механизмом сокетов ядра целесообразно применять этот вид фильтров в пространстве ядра только в системе «AF_PACKET».

```c
// contrib/linux-6.18/net/core/sock.c
// Пример установки массива инструкций в сокет.
int sk_setsockopt(struct sock *sk, int level, int optname,
		  sockptr_t optval, unsigned int optlen)
{
/* ... */
case SO_ATTACH_FILTER: {
		struct sock_fprog fprog;

		// Копирование фильтра в пространство ядра.
		ret = copy_bpf_fprog_from_user(&fprog, optval, optlen);
		if (!ret)
			// Установка фильтра в сокет.
			ret = sk_attach_filter(&fprog, sk);
		break;
	}
/* ... */
}
```

После загрузки в ядро при включенном параметре `CONFIG_BPF_JIT` ядро может выполнить JIT-компиляцию фильтра, что значительно ускорит его работу и уберёт уязвимости, основанные на предсказании работы процессора. Если же JIT-компиляцию выполнить не удалось, то ядро конвертирует массив инструкций cBPF в массив инструкций eBPF.

```c
// contrib/linux-6.18/net/core/filter.c
// Пример выполнения JIT-компиляции или преобразования в eBPF.
static struct bpf_prog *bpf_prepare_filter(struct bpf_prog *fp,
					   bpf_aux_classic_check_t trans)
{
	int err;

	fp->bpf_func = NULL;
	fp->jited = 0;

	// Проверка того, что фильтр классический.
	err = bpf_check_classic(fp->insns, fp->len);

	/* ... */

	// Выполнение платформозависимой JIT-компиляции.
	bpf_jit_compile(fp);

	// Если преобразование не удалось, то массив инструкций cBPF
	// переводится в массив инструкций eBPF.
	if (!fp->jited)
		fp = bpf_migrate_filter(fp);

	return fp;
}
```

Выгрузка фильтра из сокета происходит через системный вызов `setsockopt` с параметром `SO_DETACH_FILTER`.

### Фильтрация в пространстве пользователя

В пространстве пользователя существует множество интерпретаторов фильтров cBPF. Все они реализованы через «for» и «switch», и поэтому их работа по анализу сетевого трафика одинакова или мало отличается.

```c
// contrib/libpcap/bpf_filter.c
// Пример фильтрации в интерпретаторе библиотеки «Libpcap».
u_int
pcapint_filter_with_aux_data(const struct bpf_insn *pc, const u_char *p,
    u_int wirelen, u_int buflen, const struct pcap_bpf_aux_data *aux_data _U_)
{
	// Регистры виртуальной машины.
	register uint32_t A, X;
	// Регистр для хранения временных значений.
	register bpf_u_int32 k;
	// Помять виртуальной машины.
	uint32_t mem[BPF_MEMWORDS];

	if (pc == 0)
		return (u_int)-1;
	A = 0;
	X = 0;
	--pc;
	for (;;) { // Цикл по массиву операций.
		++pc;
		switch (pc->code) {

		default:
			abort();
		case BPF_RET|BPF_K:
			return (u_int)pc->k;

		case BPF_RET|BPF_A:
			return (u_int)A;

		/* ... */

		case BPF_MISC|BPF_TXA:
			A = X;
			continue;
		}
	}
}
```

Аналогично ядру система «DPDK» перевод массив инструкций cBPF в массив инструкций eBPF. При этом сохраняется возможность произвести JIT-компиляцию полученного массива инструкций eBPF. Но на практике, данная возможность может привести к обращению к неверному указателю, что можно увидеть в тесте `src/bpf/test_dpdk.c`, если убрать ограничение на 97-й пакет.

Чтобы создать возможность достижения скорости анализа сетевого трафика близкого к нативной функции, мной было написано преобразование фильтра из строки в код языка «C», в котором реализована функция, выполняющая фильтрацию сетевого трафика аналогично массиву инструкций cBPF. Исходный код преобразования находится в директории `src/bpf/fcc`.

## Расширенный BPF

### Устройство технологии

В 2014 году в ядро «Linux» была добавлена поддержка технологии расширенного BPF (eBPF). Основные отличия в устройстве технологий заключаются в следующем [4]:

1. число регистров увеличено до 10;
2. размер регистров увеличен до 64 бит;
3. вместо передачи двух смещений `jt`, `jf` передаётся только `jt`, а в случае неистинного исхода исполняется следующая инструкция;
4. добавлена поддержка вызовов функций ядра и верификатор фильтра.

Фильтр eBPF задаётся массивом инструкций, размер которого ограничен 4096-ю инструкциями в ядре «Linux». Инструкции сохранили размер в 64 бита, но имеют иной формат:

1. код операции (8 бит);
2. регистр, в который копируется значение (4 бита);
3. регистр, из которого копируется значение (4 бита);
4. сдвиг от текущей инструкции при истинности исхода (16 бит);
5. параметр (32 бита).

При этом количество поддерживаемых кодов операций выросло c 31-й до 87-ми [4].

Основным источником безопасности и нововведением технологии является верификатор, который проверяет массив инструкций и определяет выход за границы допустимой или вызов недоступных функций, просматривая различные ветки работы фильтра.

Из-за возможности взаимодействия с ядром «Linux» фильтры eBPF стали использоваться во множестве сценариев, которые не связаны с фильтрованием сетевого трафика, поэтому их стали называть программами BPF. Кроме того, программам стала доступна постоянная памяти, данные которой доступны в пользовательском пространстве.

### Создание фильтра

Фильтр eBPF задаётся массивом инструкций, но основным способом создания фильтров является их компиляция из исходного кода на языке «C» с помощью `clang`. Полученный ELF-файл содержит в себе один фильтр или набор фильтров, а также описание памяти, с которой фильтр взаимодействует для передачи информации между запусками, фильтрами или ядром и пользователем.

```c
// src/af_xdp/kern.c
// Пример фильтра eBPF, который в системе «AF_XDP» задаёт сокет,
// в который будет перенаправлен пакет.
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

// Основан на примере из:
//    https://github.com/xdp-project/bpf-examples/blob/main/AF_XDP-example/xdpsock_kern.c

// Максимальное количество сокетов для захвата пакетов.
#define MAX_SOCKS 32

struct {
	__uint(type, BPF_MAP_TYPE_XSKMAP); // Тип общей памяти, определяющий её реализацию.
	__uint(max_entries, MAX_SOCKS);    // Максимальное количество элементов.
	__uint(key_size, sizeof(int));     // Размер ключа для "словаря".
	__uint(value_size, sizeof(int));   // Размер значения, соответствующий некоторому ключу.
} xsks_map SEC(".maps");             // Расположение структуры в секции ".maps" ELF файла.

int num_socks = 0;          // Количество доступных сокетов.
static unsigned int num_pkts = 0; // Количество захваченных пакетов.

SEC("xdp") // Расположение функции в секции "xdp_sock" ELF файла.
int xdp_sock_prog(struct xdp_md *ctx) { // Структура xdp_md хранит данные пакета.
	const char fmt[] = "NUM %d for %d\n";
  // Отправка каждого 10-го пакета вверх по сетевому стеку
  // и вывод информации о количестве захваченных пакетов.
  if ((++num_pkts % 10) == 0) {
    bpf_trace_printk(fmt, sizeof(fmt), num_pkts, num_socks);
    return XDP_PASS;
  }
  // Функция bpf_redirect_map заполняет ряд структур в ядре,
  // что в случае успеха возвращает значение XDP_REDIRECT.
  // Вызывающая сторона в случае значения XDP_REDIRECT вызывает
  // функцию передачи пакета в нужный сокет на основе заполненных структур.
  // Распределение происходит на основе номер логического процессора.
	return bpf_redirect_map(&xsks_map, bpf_get_smp_processor_id(), XDP_DROP);
}

char _license[] SEC("license") = "GPL";
```

```sh
# src/af_xdp/Makefile
# Пример компиляции фильтра eBPF.
xdp_kern.o: kern.c
	env C_INCLUDE_PATH=/usr/include/x86_64-linux-gnu clang -g -O2 -target bpf $< -c -o $@
```

### Фильтрация в пространстве ядра

В пространство ядра массив инструкций фильтра eBPF попадает через системный вызов `bpf`. После этого пользователь может прикрепить фильтр за множеством событий.

Так при загрузке в сокет системы «AF_PACKET» с помощью системного вызова `setsockopt` с параметром `SO_ATTACH_BPF` и с файловым дескриптором фильтра, он будет аналогичен загруженному cBPF, где возвращаемое значение определяет длину полученного пакета.

Загрузка в драйвер сетевого интерфейса происходит с помощью системного вызова `bpf` с параметром `BPF_PROG_ATTACH`, что позволяет управлять пакетами с помощью возвращаемых значений `XDP_PASS`, `XDP_TX` и `XDP_REDIRECT`.

А загрузка в сокет системы «AF_XDP» происходит с помощью системного вызова `bind`, где фильтр будет выполнять аналогичные действия, что и в драйвере сетевого интерфейса.

Благодаря универсальности фильтры eBPF применяются в «AF_PACKET» и «AF_XDP».

```c
// contrib/linux-6.18/net/core/sock.c
// Пример установки массива инструкций в сокет.
int sk_setsockopt(struct sock *sk, int level, int optname,
		  sockptr_t optval, unsigned int optlen)
{
/* ... */
case SO_ATTACH_BPF:
		ret = -EINVAL;
		if (optlen == sizeof(u32)) {
			u32 ufd;

			ret = -EFAULT;
			// Копирование массива инструкций фильтра.
			if (copy_from_sockptr(&ufd, optval, sizeof(ufd)))
				break;
			// Закрепление фильтра в сокете «AF_PACKET» и др.
			ret = sk_attach_bpf(ufd, sk);
		}
		break;
/* ... */
}
```

В процессе загрузки фильтр при наличии флага `CONFIG_BPF_JIT` проходит JIT-компиляцию или же интерпретируется в функции `___bpf_prog_run`.

```c
// contrib/linux-6.18/kernel/bpf/core.c
// Пример интерпретатора фильтра eBPF.
static u64 ___bpf_prog_run(u64 *regs, const struct bpf_insn *insn)
{
	/* ... */
	u32 tail_call_cnt = 0;

// Определение макросов перехода к следующей операции.
#define CONT	 ({ insn++; goto select_insn; })
#define CONT_JMP ({ insn++; goto select_insn; })

// Переход к операции.
select_insn:
	goto *jumptable[insn->code];

	/* ... */

// Определение операции математических вычислений.
#define ALU(OPCODE, OP)					\
	ALU64_##OPCODE##_X:				\
		DST = DST OP SRC;			\
		CONT;					\
	ALU_##OPCODE##_X:				\
		DST = (u32) DST OP (u32) SRC;		\
		CONT;					\
	ALU64_##OPCODE##_K:				\
		DST = DST OP IMM;			\
		CONT;					\
	ALU_##OPCODE##_K:				\
		DST = (u32) DST OP (u32) IMM;		\
		CONT;
	// Отдельные case в switch.
	ALU(ADD,  +)
	ALU(SUB,  -)
	ALU(AND,  &)
	ALU(OR,   |)
	ALU(XOR,  ^)
	ALU(MUL,  *)
	SHT(LSH, <<)
	SHT(RSH, >>)


	// Код операции.
	STX_ATOMIC_DW:
	STX_ATOMIC_W:
	STX_ATOMIC_H:
	STX_ATOMIC_B:
		switch (IMM) {
		ATOMIC_ALU_OP(BPF_ADD, add)
		ATOMIC_ALU_OP(BPF_AND, and)
		ATOMIC_ALU_OP(BPF_OR, or)
		ATOMIC_ALU_OP(BPF_XOR, xor)

		/* ... */

			default:
				goto default_label;
			}
			break;

		default:
			goto default_label;
		}
		CONT;

	// Выход с ошибкой.
	default_label:
		pr_warn("BPF interpreter: unknown opcode %02x (imm: 0x%x)\n",
			insn->code, insn->imm);
		BUG_ON(1);
		return 0;
}
```

Выгрузка фильтра из сокета происходит через системный вызов `setsockopt` с параметром `SO_DETACH_BPF`, из драйвера сетевого интерфейса с помощью системного вызова `bpf` с параметром `BPF_PROG_DETACH` и из сокета «AF_XDP» с помощью системного вызова `bpf`.


## Фильтрация в пространстве пользователя

Для запуска фильтра eBPF в пространстве пользователя существуют различные виртуальные машины и интерпретаторы. Из рассматриваемых в работе систем только «DPDK» может интерпретировать массив инструкций фильтра или выполнить JIT-компиляцию.

Для того, чтобы создать фильтр нужно вызвать функцию `rte_bpf_elf_load` с передачей пути до ELF-файла с инструкциями eBPF и названием функции, которая будет выполнять фильтрацию. Далее можно выполнить JIT-компиляцию с помощью функции `rte_bpf_get_jit` или же вызвать интерпретатор с помощью функции `rte_bpf_exec`.

```c
// src/bpf/test_dpdk.c
// Пример функции с использованием фильтра eBPF.
void
test_ebpf_dpdk(struct pkt_descs_list* list, uint8_t is_jit) {
	// Настройка параметров работы фильтра.
	const struct rte_bpf_prm prm = {
		.prog_arg = {
			.type = RTE_BPF_ARG_PTR, // Передача в фильтр произвольного указателя.
			.size = 4096, // Размер памяти доступный по адресу.
			.buf_size = 4096, // Размер памяти доступный по адресу.
		},
	};
	struct rte_bpf* ebpf;

	/* ... */

	// Загрузка инструкций из ELF-файла.
	ebpf = rte_bpf_elf_load(&prm, "filter_ebpf.elf", "UNSPEC");
	if (!ebpf) {
		fprintf(stderr, "Error of read eBPF\n");
		return;
	}

	if (is_jit) {
		struct rte_bpf_jit jit;
		// Выполнение JIT-компиляции.
		if (rte_bpf_get_jit(ebpf, &jit) < 0) {
			/* ... */
			return;
		}

		for (size_t s_i = 0; s_i < TESTS_COUNT; ++s_i) {
			/* ... */
```

```c
// contrib/dpdk/lib/bpf/bpf_exec.c
// Пример функции интерпретации инструкций фильтра eBPF.
static inline uint64_t
bpf_exec(const struct rte_bpf *bpf, uint64_t reg[EBPF_REG_NUM])
{
	const struct ebpf_insn *ins;
	// Цикл по массиву инструкций.
	for (ins = bpf->prm.ins; ; ins++) {
		// Выполнение инструкции на основе кода операции.
		switch (ins->code) {
		case (BPF_ALU | BPF_ADD | BPF_K):
			BPF_OP_ALU_IMM(reg, ins, +, uint32_t);
			break;
		case (BPF_ALU | BPF_SUB | BPF_K):
			BPF_OP_ALU_IMM(reg, ins, -, uint32_t);
			break;
		/* ... */
		case (BPF_JMP | EBPF_CALL):
			reg[EBPF_REG_0] = bpf->prm.xsym[ins->imm].func.val(
				reg[EBPF_REG_1], reg[EBPF_REG_2],
				reg[EBPF_REG_3], reg[EBPF_REG_4],
				reg[EBPF_REG_5]);
			break;
		case (BPF_JMP | EBPF_EXIT):
			return reg[EBPF_REG_0];
		default:
			RTE_BPF_LOG_LINE(ERR,
				"%s(%p): invalid opcode %#x at pc: %#zx;",
				__func__, bpf, ins->code,
				(uintptr_t)ins - (uintptr_t)bpf->prm.ins);
			return 0;
		}
	}

	RTE_VERIFY(0);
	return 0;
}
```

### Анализ результатов

На основе результатов тестов можно заключить следующее:

1. реализация интерпретатора фильтра cBPF в библиотеке «Libpcap» обладает хорошей оптимизацией и может применяться для анализа сетевого трафика с пропускной способностью до 10 Гбит/с и выше;
2. преобразование строчного вида фильтра cBPF в исходный код языка «С» с последующей компиляцией в объектный файл даёт скорость фильтрации, сравнимую с нативным кодом, что позволяет использовать решение для анализа сетевого трафика с пропускной способностью до 40 Гбит/с и выше;
3. отключение JIT-компиляции в ядре приведёт к использованию интерпретатора, который много медленнее анализирует сетевой трафик;
4. фильтрация с помощью eBPF в ядре после JIT-компиляции позволяет анализировать сетевой трафик с пропускной способностью до 40 Гбит/с и выше;
5. фильтрация с помощью eBPF в «DPDK» после JIT-компиляции позволяет анализировать сетевой трафик с пропускной способностью до 40 Гбит/с и выше;
6. JIT-компиляция фильтра eBPF, полученного из фильтра cBPF, может привести к неправильной работе с памятью;
7. в системе «AF_PACKET» для фильтрации в пространстве ядра наиболее быстрым решением является использование eBPF;
8. в системе «AF_XDP» по умолчанию используется лучшее решение для анализа трафика в пространстве ядре, а именно — eBPF;
9. в пространстве пользователя получить схожие результаты можно через использование «DPDK» и фильтра eBPF с JIT-компиляцией или через использование нативного кода полученного из фильтра cBPF;
10. в нетребовательных решениях достаточно использования интерпретатора из библиотеки «Libpcap».
