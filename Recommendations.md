От количества очередей получения трафика зависит пропускная способность системы. В сетевом стеке ядра «Linux», по умолчанию, количество очередей получения трафика равно количеству доступных логических процессоров. В системах захвата сетевого трафика «AF_PACKET» и «DPDK» количество очередей определяется динамически в процессе инициализации системы захвата, тогда как в системе «AF_XDP» количество очередей определяется настройками сетевого стека, а при их несовпадении может возникнуть состояние гонки или потеря трафика.

Чтобы добиться максимальной производительности используется метод распределения пакетов на основе номера логического процессора. Пакет будет направлен в ту очередь, номер которой совпадает с номером логического процессора. Такой метод позволяет избавиться от необходимости синхронизации доступа к очереди различными логическими процессорами, тем самым избавившись от дорогих операций:

- обращение к планировщику, смена контекстов процессов и ожидание события [1];
- использование атомарных операций [2].

Фильтрация сетевого трафика может быть реализована технологиями: классический BPF или расширенный BPF. При этом эти фильтры двух этих технологий с помощью JIT-компиляции преобразуются в нативный код системы и могут использоваться, как обычные функции.  

Фильтрация трафика при захвате задается либо с помощью строкового pcap-фильтра, либо с помощью исходного кода функции Фильтрации. Первый метод задания фильтрации используется для создания cBPF-фильтров (и eBPF-фильтров при конвертации из cBPF-фильтров), а второй метод используется для eBPF-фильтров или для создания функций фильтрации в исходном коде системы.

Способ фильтрации трафика определяет скорость работы фильтра. Можно выделить следующие способы фильтрации:

1. интерпретатор cBPF в библиотеке «Libpcap» со средней скоростью работы;
2. интерпретатор cBPF (конвертация в eBPF) в ядре «Linux» с низкой скоростью работы;
3. интерпретатор cBPF (конвертация в eBPF) в системе «DPDK» с низкой скоростью работы;
4. компиляция cBPF в нативный код с высокой скоростью работы;
5. JIT-компиляция сBPF (конвертация в eBPF) в ядре «Linux» со средней скоростью работы;
6. интерпретатор eBPF в ядре «Linux» с низкой скоростью работы;
7. интерпретатор eBPF в системе «DPDK» с низкой скоростью работы;
8. JIT-компиляция eBPF в системе «DPDK» с высокой скоростью работы;
9. нативный код функции фильтрации с высокой скоростью работы.

При конвертация cBPF в eBPF в системе «DPDK» допускаются ошибки.

Все рекомендации по проектированию работы очередей получения трафика аналогичны рекомендациям по проектированию работы очередей отправки трафика, но с одной особенностью, что при раздельной работе очередей получения и отправки трафика сетевого устройства их количество может отличаться и определяется либо сетевым стеком при использовании системы «AF_PACKET» или «AF_XDP», либо настройками пользователя в системе «DPDK».

Создание трафика в разрабатываемом решении требует либо ручной реализации необходимого стека протоколов канального, сетевого и транспортного уровней, либо готового стека протоколов пользовательского пространства (например, «mTCP»). В таком случае, данные пакета копируются в очередь отправки сетевого трафика.

Взятие пакетов из очередей получения сетевого трафика не требует дополнительных действий для их отправки. Так в системах «AF_XDP» и «DPDK» предусмотрены функции для использования одних и тех же дескрипторов для получения и отправки без копирования данных пакетов.

Подробное описание процесса настройки сетевого стека ядра «Linux» содержится в разделе [настройки сетевых интерфейсов](Settings-of-interfaces.md).

Подробное описание процесса применения системы «AF_PACKET» содержится в разделе [разбора примеров «AF_PACKET»](AF_PACKET.md).

Подробное описание процесса применения системы «AF_XDP» содержится в разделе [разбора примеров «AF_XDP»](AF_XDP.md).

Получение названия драйвера сетевого интерфейса возможно с помощью команды `ethtool --driver IFNAME`, где `IFNAME` изучаемый сетевой интерфейс.

Просмотр `VID` и `PID` сетевого интерфейса возможен с помощью команды `lspci -nn`.

Просмотр характеристик сетевого интерфейса возможен помощью утилиты `ethtool -i IFNAME`, где `IFNAME` изучаемый сетевой интерфейс.

Поддержка системы «AF_XDP» в исходном коде драйвера определяется по наличию флага `NETDEV_XDP_ACT_XSK_ZEROCOPY` в процессе инициализации сетевого интерфейса.

Поддержка системы «DPDK» определяется наличием пользовательского драйвера в дереве исходного кода «DPDK».

Получение количества ядер на один процессор и количества NUMA-узлов  возможно с помощью команды `lscpu`.

Получение суммарного объема доступной оперативной памяти возможно с помощью утилиты `free`.

Получение объема локальной памяти для каждого процессора возможно с помощью утилиты `numactl`.

Полученные размера кеш-памяти для каждого процессора также возможно через `lscpu`.

Определение необходимой скорости работы системы и определение сложности обработки сетевого трафика происходит их задач, которые должно выполнять разрабатываемое решение.

Если выбор системы захвата сетевого трафика основан на ограничениях сетевой карты, то лучшим решением будет правильно настроенная система «AF_PACKET», так как большинство современных сетевых карт имеют поддержку системы «DPDK» и «AF_XDP».

Если выбор системы захвата сетевого трафика основан на ограничениях вычислительных возможностей устройства, то лучшим решением также будет система «AF_PACKET», которая использует общую память между пространствами для передачи пакетов, но без активного ожидания пакетов, что существенно снижает нагрузку на процессор.

Если выбор системы захвата сетевого трафика основан на необходимости поддержки требуемой скорости передачи трафика, то лучшим решением при скорости трафика от 10 Гб/с будет являться система «DPDK», а при меньшей скорости оптимальным будет выбор системы «AF_XDP».

Если выбор системы захвата сетевого трафика основан на необходимости минимизации задержки сетевых пакетов, то лучшим решением будет система «DPDK» с активным режимом ожидания.

Если выбор системы захвата сетевого трафика основан на сложности обработки сетевого трафика, то лучшим решением будет система «DPDK» из-за большого количества настроек конфигурирования процесса захвата и синхронизации общих данных.
